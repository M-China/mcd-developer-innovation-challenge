# 麦当劳 Wrapped · 年度消费报告

用麦当劳 MCP 的历史订单数据，给用户生成一份 Spotify Wrapped 风格的消费报告：总花费、订单数、客单价、0 元单、最常点商品、招牌组合、时段/门店/城市分布、消费人格认证，最后给出个性化点单建议。

0 元单可能是抖音/美团等站外团购券的到店核销——钱实际花在了站外。所以本 skill 支持**用户自主补录站外购买记录**，把 0 元核销单还原成真实消费，避免把"花 25 块买的团购券"算成"麦当劳免费请客"。

## 工作流

1. **拉数据**：调用 MCP 工具 `order-list`（无参数，一次返回全部历史订单）。
2. **0 元单甄别与补录**：读取 `<工作区>/mcd-wrapped-records.json`（补录记录，可能不存在），按「站外购买补录」处理：
   - 文件存在 → 直接合并，不再询问。
   - 文件不存在且检测到 0 元单 → **询问用户一次**："检测到 N 笔 0 元核销单，可能是抖音/美团团购券核销。要补录站外购买记录吗？可以直接把记录粘给我（日期 / 渠道 / 实付金额 / 商品），或说'不用'按纯免费处理。" 用户拒绝、或处于无人值守无法交互 → 按纯免费口径，并在报告脚注注明该口径。
   - 没有 0 元单 → 跳过。
3. **清洗**：按「数据契约」解析；剔除 `orderStatus` 含"取消/退款"的订单并单独记录。
4. **算指标**：按「指标口径」计算，不要临场发明算法。
5. **判人格**：按「人格判定表」顺序匹配，第一条命中即停。
6. **出报告**：读取本 skill 目录下的 `assets/wrapped-template.html`，替换全部 `{{TOKENS}}`，保存为独立 HTML 文件（任何浏览器可直接打开，便于用户截图分享）。若在 ZCode 桌面端（有会话可视化目录），按其内联渲染规范另出一份主题适配的片段展示给用户。
7. **给建议**：按「个性化建议」生成 2-3 条。建议只输出文字，未经用户确认禁止调用 `create-order`。

## 数据契约（来自 mcd-mcp `order-list` 实测）

```json
{
  "orderId": "1030000000000000000000000001",
  "orderType": "1",              // 1=到店, 2=外送
  "createTime": "2026-06-18 12:30:00",
  "beType": "1",                 // 1=到店自取, 2=麦乐送, 5=得来速, 6=企业团餐
  "storeCode": "1990999",
  "storeName": "麦当劳江城中山路餐厅",
  "orderStatus": "订单已完成",
  "orderProductList": [{
    "productCode": "9900016279", "productName": "龙焰鸡腿双堡", "quantity": 1,
    "comboItemList": [{ "productCode": "1406", "name": "板烧鸡腿堡", "quantity": 1 }]
  }],
  "realTotalAmount": "0"
}
```

以上 orderId、storeCode、storeName、createTime 均为虚构示例，仅结构真实。

关键坑（每一条都来自真实返回，务必遵守）：

- `realTotalAmount` 是**元**为单位的字符串（如 `"13.5"`），用 `Number()` 解析。`"0"` 表示应用内实付 0 元——可能是券/积分兑换，**也可能是站外团购券核销**，先走补录甄别再下结论。
- 套餐子项在 `comboItemList[]` 里，字段名是 **`name`**（不是 `productName`）。统计商品频次时主商品和套餐子项都要计入，否则薯条会凭空消失。
- 接口没有分页参数，一次返回全部；订单可能只有个位数——数据少报告照样要好玩，不要因为样本小而拒绝生成。
- 城市从 `storeName` 里直接读（城市名通常紧跟"麦当劳"，如"麦当劳**江城**中山路餐厅"），由你自己识别，不要写脆弱的字符串切割规则。
- `createTime` 格式 `YYYY-MM-DD HH:mm:ss`，时段划分取小时数。

## 站外购买补录（用户自填）

记录文件固定为 `<工作区>/mcd-wrapped-records.json`，schema：

```json
{
  "records": [
    {
      "date": "2026-08-15",
      "channel": "抖音团购",
      "amount": 25.0,
      "items": "双人套餐（汉堡 ×2 + 薯条 ×2 + 饮料 ×2）",
      "matchOrderId": "1030000000000000000000000002",
      "matchProductName": "非「泥」莫「薯」",
      "note": "自动匹配：日期一致且为 0 元核销单"
    }
  ]
}
```

（示例记录同样为虚构。）

- `amount` 一律为**元**的数值；`matchOrderId` 可空；其余字段按用户口述填。
- `matchProductName` 可选：站外券只覆盖订单里的**部分商品**时（混合单），填对应 `orderProductList[].productName`，金额只记该券；缺省视为整单核销。
- **两种入口**：
  - 报告流程中询问后补录：解析用户粘贴的记录 → 写入文件 → 回显确认。写入后重跑报告不再重复询问。
  - 独立补录：用户任何时候说"记一笔麦当劳团购""我在抖音买了个 29.9 的套餐"→ 只解析、写文件、回显确认即可；**不要**自动生成整份报告，除非用户明确要求。
- **匹配规则**：`matchOrderId` 缺省时，按"日期最近 + 商品描述相似"推断关联订单，匹配依据写进 `note`；匹配不上就留空（该记录作为独立一餐计入）。0 元单必问；但补录入口接受**任意订单**的站外券记录——App 内已实付的订单也可能混着站外券买的商品（混合单），用户主动报了就照录。
- 日期缺年份 → 取报告年份；月份对不上就近年份 → 向用户确认一次。
- 文件损坏或某条字段缺失 → 跳过坏行、继续统计，并在回复里告知用户哪条没算进去；不要让整份报告失败。
- 隐私：记录只存本地工作区，报告里只出现聚合金额和渠道名。

## 指标口径

- **应用内总花费** = 所有未取消订单 `realTotalAmount` 之和。
- **站外实付** = Σ `records[].amount`（无补录记录时为 0）。
- **真实总花费** = 应用内总花费 + 站外实付。报告主数字用这个口径。
- **订单数** = 未取消订单条数（应用内）。
- **体验次数** = 订单数 + 未匹配到订单的补录记录数。
- **综合客单价** = 真实总花费 ÷ 体验次数（报告主卡用这个；无补录时它等于应用内客单价）。
- **团购核销单** = App 内实付 0 元、整单由站外券覆盖的订单。
- **混合单** = 同一订单里既有 App 内实付、又有匹配到补录记录的核销商品；此时站外实付按券金额计，App 内实付照常计入，**勿重复计算**。
- **薅羊毛单数** = 整单 0 元且未匹配任何补录记录的订单数；**0 元单占比** = 薅羊毛单数 ÷ 订单数。
- **最常点 TOP5**：按 `productCode` 聚合 `quantity`（主商品 + 套餐子项合并），展示商品名，按数量降序，同数量按最近下单时间排前。补录记录的商品是自由文本，只在「站外账本」里展示，不参与商品频次统计。
- **招牌组合**：取商品数量最多的一单的完整组成，起一个短绰号（如"双堡双薯"）。
- **时段**：清晨 <10 / 午市 10-14 / 下午茶 14-17 / 晚市 17-21 / 深夜 ≥21。补录记录按其 `date` 无法定位时段，不参与时段统计。
- **时间跨度**：最早订单/记录月 ~ 最晚订单/记录月。

## 人格判定表（按顺序匹配，第一条命中即停）

| 条件 | 人格 |
| --- | --- |
| 深夜单（≥21 点）占比 ≥ 40% | 深夜麦门信徒 |
| 站外实付 ÷ 真实总花费 ≥ 50% | 团购精算师 |
| 0 元单（未匹配）占比 ≥ 50% | 羊毛党麦门圣徒 |
| 薯条/小食类数量排第一 | 薯条鉴赏家 |
| 外送单占比 ≥ 60% | 沙发薯条学家 |
| 订单数 + 补录记录数 < 5 | 新晋麦门教徒 |
| 其他 | 经典巨无霸信徒 |

每条人格配一句**基于真实数据的判词**，例如："3 单里 2 单一分钱没花，是麦当劳在请你吃饭。"若触发「团购精算师」，判词要点破站外购票的省钱属性，如："一半的钱花在抖音下单，进店只负责喊'取餐'。"

## 报告生成

- 模板：`assets/wrapped-template.html`（独立 HTML，自带深色+金红主题，浏览器直接打开）。
- 替换所有 `{{TOKENS}}`；可复制/删减标注了 `<!-- ROW:xxx -->` 的行块；「站外账本」整段是可选的，无补录记录时删除该段并把后续编号顺延。
- 有补录记录时：主数字用真实总花费，`{{SPEND_CAP}}` 注明口径（如"含站外团购实付 ¥25"）；年度账本四张卡换成综合客单价/团购核销单/站外实付等更有信息量的口径。
- 保存位置：`<工作区>/demo/mcd-wrapped-<年份>.html`。
- **隐私红线**：报告里不出现 orderId、手机号、地址；订单明细最多展示最近 3 单的摘要。
- 报告末尾固定一行数据来源说明："数据来自麦当劳 MCP · order-list + 用户自补录的站外购买记录，仅含本人账号"。

## 个性化建议

结合报告结论给 2-3 条，可调用 `available-coupons`（麦麦省可领券）或 `query-my-coupons`（卡包）让建议落到真实优惠上：

- 团购核销占比高 → 提示继续比价站外渠道，同时关注应用内同类套餐券。
- 0 元单（未匹配）占比高 → 提示积分/抽奖/兑换玩法别浪费。
- 时段集中 → 提示对应时段的活动（如下午茶时段甜品优惠）。
- 消费偏低/订单少 → 提示麦麦省领券、新人活动。
- 有明显空档月份 → 轻调侃 + 提示当月活动日历（`campaign-calendar`）。

规则：建议必须是文字；用户明确说"领券/下单"后才调用对应工具，禁止自动下单。

## 错误处理

- `order-list` 返回空列表或全是已取消订单 → 生成「麦门新人版」报告：指标全 0，人格固定「新晋麦门教徒」，判词写"你的麦门故事还停在第一页"，并引导用户点第一单后重跑。
- 接口报错 → 重试一次；仍失败则如实告知用户稍后再试。**不要编造数据**。
- 字段缺失（如某单无 `comboItemList`）→ 跳过该子结构继续统计，报告中不受影响。
- 补录文件 JSON 损坏 → 忽略坏行并在回复中告知，报告流程继续。
